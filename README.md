# 防汛雨量数据平台

把雨量站主、备翻斗计的**累计脉冲计数**转换为可信的 **UTC 小时降雨量**，并把日内连续有雨的小时
合成**降雨过程**（带稳定编号与替代关系），供预警模型取数、防汛研判员追溯。
Flask + SQLite，网页上传/查询 + 等效 JSON API，Docker Compose 一键启动。

## 快速开始

```bash
docker compose up --build
# 打开 http://localhost:8000
```

数据库文件保存在命名卷 `rainfall-data`（容器内 `/data/rainfall.db`），重启后数据仍可查询。

本地开发（无需 Docker）：

```bash
pip install -r requirements.txt
python -m app.app                 # 开发服务器，监听 8000
# 或生产形态（与 Docker CMD 相同）：
gunicorn --bind 0.0.0.0:8000 --workers 1 --threads 8 "app.app:create_app()"
```

运行自测（53 个用例）：

```bash
python -m unittest discover -s tests -v
```

## CSV 格式

列顺序：`站点, 主备标记, UTC整分钟, 计数(0~9999), 修订号`；表头可选（支持中英文列名），无表头时按此顺序解析。

```csv
station,device,minute,counter,revision
ST01,primary,2026-11-17T10:00:00Z,9980,1
ST01,backup,2026-11-17T10:00:00Z,120,1
```

- **站点**：非空字符串（≤64 字符）。
- **主备标记**：`primary`/`backup`，也接受 `主`/`备` 等别名。
- **UTC 整分钟**：如 `2026-11-17T10:00:00Z`、`2026-11-17 10:00`；未带时区按 UTC 处理，带偏移会换算成 UTC；秒必须为 00。
- **计数**：整数 0~9999。
- **修订号**：非负整数。同一（站点, 设备, 分钟）**只接受更高修订号**，否则该行被拒绝并记入批次报告。

示例文件：`examples/sample.csv`（含完整小时、备计、回绕、缺口四种情形）；
`examples/process.csv`（2026-11-18 06:00~09:00 连续有雨，上传后生成一个降雨过程）。

## 计算规则

- 每小时 = 60 个相邻分钟间隔（整点 H:00 至下一整点，共 61 个端点）。
- 每个间隔：**主计两端齐全取主计差值，否则备计两端齐全取备计差值，绝不跨设备相减**；两端都无可用数据则该间隔缺失。
- 计数下降按一次 10000 回绕处理：差值 = (末 − 初) mod 10000。
- 每脉冲 0.2 mm；**任一间隔缺失则整小时不可供数**（`status=incomplete`，`rainfall_mm=null`），网页会标出缺口与每段来源。

## 降雨过程目录

按**站点 + UTC 自然日**生成日内降雨过程目录：

- **只用可供数小时**：雨量大于 0 的连续可供数小时合成一段；**零雨量或不可供数小时断开**。
- 每段列出**开始、结束、小时数、累计雨量和编号**（编号形如 `ST01-20261117-1`，站点+日期+递增序号，序号永不复用）。
- 补传/修订读数后，受影响日期的目录在**同一事务**内重算：
  - **起止及累计雨量未变**的过程**沿用编号**；
  - 变化的旧编号置为"已被替代"，**保留原结果**（起止、累计雨量、创建批次）永久可查；
  - 旧编号与新编号按**共有降雨小时**建立**直接替代关联**：一个旧编号对应多个新编号为**拆分**，多个旧编号指向同一新编号为**合并**，无替代过程为**消失**，均可在过程页/ API 查询；
  - **整点修订可影响相邻两日**（午夜 00:00Z 读数同时是前一日 23 时的末点与当日 00 时的起点），两日目录在同一批次内一起更新。
- 过程编号被替代后不会复活：与之完全相同的过程再次出现时发新编号，旧编号及其历史保持可查。

## 接口

| 接口 | 说明 |
|---|---|
| `GET /` | 首页：上传、查询、站点与批次列表 |
| `POST /upload` | 网页上传（文件或粘贴文本），返回批次报告页（含目录变更） |
| `POST /api/upload` | 同上，JSON 返回（`catalog_changes` 为受影响日期的目录变更） |
| `GET /report?station=..&hour=..` | 网页小时报告（雨量、缺口、每段来源） |
| `GET /api/hourly?station=..&hour=..` | 等效 JSON（与网页同一计算入口，结果一致） |
| `GET /day?station=..&date=..` | 网页过程目录（当日过程、逐小时雨量、历史编号） |
| `GET /api/processes?station=..&date=..` | 等效 JSON（`processes` 当前目录 + `hours` 逐小时） |
| `GET /process/<编号>` | 网页过程详情（原结果、直接替代、被替代关系） |
| `GET /api/process/<编号>` | 等效 JSON（`replacements`/`predecessors` 含共有降雨小时） |
| `GET /api/stations` | 站点数据范围 |
| `GET /api/batches` | 上传批次列表 |
| `GET /batches/<id>` | 批次行级明细与该批次的目录变更 |
| `GET /api/health` | 健康检查 |

`hour` 需整点对齐（如 `2026-11-17T10:00Z`），`date` 为 UTC 自然日（如 `2026-11-17`）。
预警模型取数时请检查 `status == "ok"` 再使用 `rainfall_mm`；过程编号交给模型后，
补传读数可用 `GET /api/process/<编号>` 追查其变化（沿用 / 替代 / 消失）。

## 一致性与可靠性设计

- **两小时一致**：小时雨量由 `readings` 表现算现算（无缓存），补传或修订整点读数提交后，前后两小时立即同时反映新值；网页与 API 共用同一计算函数。
- **目录与读数同批生效**：每批上传的读数、批次记录、行级明细与**受影响日期的过程目录**在**单个事务**中写入，任何失败（含目录重算失败）整体回滚，不留半批新结果。
- **不新旧混用**：每个请求在同一读快照中完成全部查询（请求级事务），网页与 API 的单次响应不会混用提交前后的状态。
- **持久化**：过程目录与替代关联存于 SQLite（WAL 模式）落盘于挂载卷，重启后新旧编号仍可查询。
- **并发**：单 gunicorn worker 多线程 + SQLite 写事务串行化与 `busy_timeout`。

## 目录结构

```
app/
  core.py        # 纯逻辑：CSV 解析校验、小时雨量计算、日内过程分段（不依赖 Flask/SQLite）
  db.py          # SQLite：模式、事务性批量入库、过程目录重算与查询
  app.py         # Flask 路由（网页 + API）
  templates/     # 页面模板
tests/           # 53 个自测用例（test_app.py 平台基础，test_processes.py 过程目录）
examples/        # sample.csv 小时样例；process.csv 降雨过程样例
Dockerfile / docker-compose.yml / requirements.txt
```
